## 1. 这是什么 · 能力总览

cmx-rulesengine 是用 **Rust** 编写、可独立部署的**决策规则引擎微服务**，对标 GoRules ZEN、Camunda DMN、Drools、IBM ODM。它把业务规则从代码中抽出，用**决策表**和**决策图**声明式表达，通过 HTTP API 求值。

**核心能力：**

| 能力 | 说明 | 对标 |
|------|------|------|
| 决策表 | 输入列 × 规则行 × 输出列，11 种 DMN 命中策略 | OMG DMN 决策表 |
| 决策图（JDM） | 多张决策表/表达式/子决策编排成 DAG，数据左→右流经累积 | GoRules JDM |
| FEEL 表达式 | 完整 FEEL 子集：算术/比较/逻辑/条件/列表/量词/内置函数库 | DMN FEEL |
| **失败归因 trace** | 精确定位"哪个节点、哪条规则、哪个输入列、为什么失败" | **超越 ZEN** |
| **gap / overlap 分析** | 决策表是否存在**空隙**（未覆盖组合）、**重叠**（多规则同时命中） | **超越 ZEN** |
| 版本与发布 | 草稿 → 不可变发布（内容哈希 rev）→ 版本激活 | DMN 部署 |
| 决策日志/审计 | 每次求值一条日志，含全量 trace，供合规还原 | IBM ODM Decision Warehouse |
| 测试用例/回归 | 用例集批跑 diff 期望 + 通过率 + 覆盖率 | — |
| 多租户 | db-per-tenant 物理隔离 | — |
| 可视化工作台 | 设计器 / 仿真台 / 审计中心（浏览器四区界面） | GoRules Editor |

**架构（一芯多壳）：**

- **芯** `cmx-rule-app`：平台中立应用层，`rule_routes::<S>()` 对任意 host 泛型成立。
- **壳①** 独立微服务 `cmx-rule-server`（本手册主角，端口 8094）。
- **壳②** 门户内嵌反代（cmx-container 平台经 `cmx-rule-api` 挂 `/api/rules/*`）。
- **壳③** 可嵌 Web Component（`web/elements/*`）。

三壳复用同一套 handler + 路由 + 引擎，零业务漂移。

**crate 组成：**

| crate | 职责 |
|-------|------|
| `cmx-rule-model` | 语义中立内核：IR（决策表/图）、求值上下文、trace、存储 trait、约束分析类型 |
| `cmx-rule-feel` | FEEL unary test + 完整表达式引擎（tokenizer + Pratt 解析 + 求值 + 内置函数） |
| `cmx-rule-engine` | 决策求值内核：11 命中策略、图拓扑求值、gap/overlap 分析算法 |
| `cmx-rule-store-pg` | PostgreSQL 存储（4 张表，无外键，DDL 幂等） |
| `cmx-rule-app` | axum handler + 路由 + 认证 + 多租户 + 大盘 + native-pages 投递 |
| `cmx-rule-server` | 独立二进制（chassis 装配，端口 8094，无 poller 纯请求驱动） |

## 2. 五分钟上手

### 2.1 启动服务

```bash
cd cmx-rulesengine
./rules.sh            # = cargo run -p cmx-rule-server；bin 自动读 .env（CONFIG_FILE 指向 rules-server.toml）
# 或指定配置文件：
CONFIG_FILE=./rules-server-inner.toml ./rules.sh
```

启动成功后：

- `http://127.0.0.1:8094/` —— 决策引擎监控大盘
- `http://127.0.0.1:8094/api/rules/v1/definitions` —— 决策定义列表
- `http://127.0.0.1:8094/api/rules/v1/openapi.json` —— OpenAPI 文档
- `http://127.0.0.1:8094/_mon` —— 技术监控（系统/DB池/请求遥测）

### 2.2 灌演示数据（可选）

```bash
./seed-demo.sh        # 灌 4 个决策 + 3 用例 + 6 条决策日志
```

### 2.3 创建一个决策表

```bash
curl -XPOST http://127.0.0.1:8094/api/rules/v1/definitions/draft \
  -H 'Content-Type: application/json' -d '{
  "key": "credit_approval",
  "name": "信贷审批",
  "kind": "decisionTable",
  "hitPolicy": "U",
  "inputs": [
    { "id": "i1", "label": "信用分", "expression": "score" },
    { "id": "i2", "label": "地区",   "expression": "region" }
  ],
  "outputs": [
    { "id": "o1", "name": "tier",     "label": "等级" },
    { "id": "o2", "name": "maxLimit", "label": "额度上限" }
  ],
  "rules": [
    { "inputEntries": [">= 750", "-"],            "outputEntries": ["\"A\"", "income * 5"] },
    { "inputEntries": ["[650..750)", "\"north\""], "outputEntries": ["\"B\"", "income * 4"] },
    { "inputEntries": ["[650..750)", "-"],         "outputEntries": ["\"B\"", "income * 3"] },
    { "inputEntries": ["< 650", "-"],             "outputEntries": ["\"C\"", "0"] }
  ]
}'
```

### 2.4 求值

```bash
curl -XPOST http://127.0.0.1:8094/api/rules/v1/decisions/credit_approval/evaluate \
  -H 'Content-Type: application/json' \
  -d '{"input":{"score":800,"region":"north","income":10000}}'
```

响应：

```json
{
  "code": 0, "msg": "success",
  "data": {
    "output": { "tier": "A", "maxLimit": 50000.0 },
    "logId": "…uuid…",
    "timingUs": 120,
    "trace": [ { "nodeId": "decisionTable", "nodeKind": "decisionTable",
                 "matchedRules": [0], "input": {…}, "output": {…}, "failure": null } ]
  }
}
```

## 3. 核心概念

| 概念 | 含义 |
|------|------|
| **决策（Decision）** | 一个由稳定 `key` 寻址的规则单元，可以是**决策表**或**决策图**。 |
| **key** | 业务键，跨版本不变，求值按它寻址。英数下划线，PRIMARY KEY。 |
| **草稿（draft）** | `POST /definitions/draft` 存的可编辑定义，存于 `cmx_rule_definition` 表。 |
| **发布（release）** | 把当前草稿快照成**不可变**版本，version+1，写 `cmx_rule_release`，带内容哈希 `rev`。 |
| **激活版本（active）** | 求值时装载的版本。发布默认激活；可 `activate` 切回旧版。 |
| **输入事实（input facts）** | 求值时传入的 JSON 对象，决策表输入列表达式从中取值。 |
| **命中策略（hit policy）** | 多条规则同时命中时如何裁决输出（唯一/首个/收集/求和…）。 |
| **trace** | 逐节点求值轨迹，含输入快照、输出、命中行、**失败归因**。 |
| **决策日志（decision log）** | 每次求值落一条审计记录（除非 `options.log=false`）。 |
| **测试用例（test case）** | 输入 → 期望输出，供回归批跑与覆盖率统计。 |

**决策的生命周期：**

```
新建草稿 ──draft──> [草稿态] ──publish──> [已发布 v1] ──publish──> [已发布 v2]
                       │                        │                      │
                    evaluate                activate v1            (激活最新)
                    （草稿可试算）          （切回旧版求值）
                       │
                    delete（连带清理发布/日志/用例四表）
```

> **装载优先级**：`GET /definitions/{key}` 与求值装载定义时，**优先取激活发布版**（`cmx_rule_release WHERE active=TRUE`）；无发布则回退草稿（`cmx_rule_definition`）。因此设计期可直接对草稿 `evaluate` 试算。

## 4. 决策定义详解（DecisionDef）

`DecisionDef` 是设计器产物 + 引擎输入，JSON 顶层结构：

```jsonc
{
  "key": "credit_approval",   // 必填。稳定业务键，求值按它寻址
  "name": "信贷审批",          // 可选。展示名，默认空串
  "version": 1,               // 可选。版本号，默认 1
  "kind": "decisionTable",    // 必填。决策体类型标签："decisionTable" | "graph"
  // …决策体字段随 kind 平铺进顶层…
}
```

`kind` 字段是 serde internally-tagged 判别器，决定后续字段形状：

- `kind: "decisionTable"` → 顶层平铺 `hitPolicy` / `inputs` / `outputs` / `rules`
- `kind: "graph"` → 顶层平铺 `nodes` / `edges`

### 4.1 决策表 DecisionTable

最常用的决策形态：一张二维表。

```jsonc
{
  "key": "discount_tier",
  "name": "折扣分级",
  "kind": "decisionTable",
  "hitPolicy": "F",            // 命中策略，默认 "U"
  "inputs":  [ /* 输入列 */ ],
  "outputs": [ /* 输出列 */ ],
  "rules":   [ /* 规则行 */ ]
}
```

**求值语义**：对每条规则行，逐输入列取值 → 该列 unary test 判真（行内各列 **AND**）→ 全真则该行命中 → 按命中策略汇总所有命中行的输出。

**结构校验（`validate`）**：

- 至少一个输出列（`outputs` 非空），否则报错 `决策表至少需一个输出列`。
- 每条规则行的 `inputEntries` 长度必须 = `inputs.len()`。
- 每条规则行的 `outputEntries` 长度必须 = `outputs.len()`。

### 4.2 命中策略 HitPolicy（11 种）

序列化用 DMN 标准单字母代号，便于与 DMN/Camunda/Drools 互通。

| 代号 | 名称 | 返回 | 语义 |
|------|------|------|------|
| `U` | Unique 唯一 | 单个对象 | **至多一行命中**；≥2 行命中视为错误（触发失败归因）。**默认**。 |
| `A` | Any 任意 | 单个对象 | 可多行命中，但**所有命中行输出必须一致**，取其一；不一致报错。 |
| `P` | Priority 优先 | 单个对象 | 多命中按输出优先级取最高。*R0/R1 退化为取行序首个*。 |
| `F` | First 首个 | 单个对象 | 按行序取**首个**命中（DMN 视为不良实践，慎用）。 |
| `C` | Collect 收集 | **数组** | 返回所有命中行输出的列表（无序，实现按行序）。 |
| `R` | RuleOrder 规则序 | **数组** | 返回所有命中行输出，按规则行序。 |
| `O` | OutputOrder 输出序 | 单个对象 | 按输出优先级序。*R0/R1 退化为取行序首个*。 |
| `C+` | Collect Sum 求和 | **数值** | 命中行**单一输出列**求和。 |
| `C<` | Collect Min 最小 | **数值** | 命中行单一输出列取最小。 |
| `C>` | Collect Max 最大 | **数值** | 命中行单一输出列取最大。 |
| `C#` | Collect Count 计数 | **整数** | 命中行数。 |

**无命中时的返回**：

- `U` / `A` / `P` / `F` / `O` → `null`
- `C` / `R` → `[]`（空数组）
- `C#` → `0`
- `C+` → `0.0`

**聚合策略约束**（`C+` / `C<` / `C>`）：要求决策表**恰好一个输出列**且所有命中值为数值，否则失败归因。

**示例**（同一表三行全通配命中，输出列 `amount` = 10/30/20）：

| 策略 | 输出 |
|------|------|
| `C#` | `3` |
| `C+` | `60.0` |
| `C<` | `10.0` |
| `C>` | `30.0` |
| `C`  | `[{"amount":10.0},{"amount":30.0},{"amount":20.0}]` |

### 4.3 输入列 / 输出列 / 规则行

**输入列 InputClause：**

```jsonc
{
  "id": "i1",             // 可选。列 id，供 trace / gap-overlap 引用
  "label": "信用分",       // 可选。展示名（业务可读）
  "expression": "score"   // 必填。取值表达式，从输入事实取该列待测值
}
```

`expression` 求值：R0 是 JSON 路径（`amount` / `order.amount` / `items.0.qty`），R1 起是完整 FEEL 表达式。取值缺失 → `null`（不 panic）。

> **路径语义**：整名精确命中平坦 key 优先（历史数据存了带点号的字面量 key 时），否则逐段下钻（对象取字段、数组取数字下标）。

**输出列 OutputClause：**

```jsonc
{
  "id": "o1",          // 可选。列 id
  "label": "等级",      // 可选。展示名
  "name": "tier"       // 必填。输出对象的键名（命中行该列值写入 output[name]）
}
```

**规则行 DecisionRule：**

```jsonc
{
  "id": "r1",                              // 可选。规则 id（协同编辑/trace 稳定键）
  "inputEntries": [">= 750", "-"],         // 必填。每输入列一个 unary test；长度 = inputs.len()
  "outputEntries": ["\"A\"", "income * 5"], // 必填。每输出列一个 FEEL 表达式；长度 = outputs.len()
  "annotation": "高分优质客户"               // 可选。规则注释
}
```

- `inputEntries[i]`：unary test（详见 §5.1）。`-` 或空串 = 通配（恒真，该列不参与判定）。
- `outputEntries[j]`：完整 FEEL 表达式（详见 §5.2），可引用输入事实（如 `income * 5`、`if score>700 then "A" else "B"`）。

### 4.4 决策图 DecisionGraph（JDM）

把多个决策单元编排成有向无环图（DAG），对标 GoRules JDM：**数据从 input 节点左→右流经各节点，输出并入累积上下文**。

```jsonc
{
  "key": "loan_decision",
  "name": "贷款综合决策",
  "kind": "graph",
  "nodes": [
    { "id": "in",   "type": "input" },
    { "id": "base", "type": "decisionTable", "table": { /* 完整 DecisionTable */ } },
    { "id": "risk", "type": "decision", "decisionKey": "risk_score" },
    { "id": "calc", "type": "expression", "mappings": [
        { "key": "maxLimit", "expression": "income * rate" }
    ]},
    { "id": "out",  "type": "output" }
  ],
  "edges": [
    { "source": "in",   "target": "base" },
    { "source": "base", "target": "risk" },
    { "source": "risk", "target": "calc" },
    { "source": "calc", "target": "out" }
  ]
}
```

**节点类型（`type`）：**

| 类型 | 专属字段 | 作用 |
|------|---------|------|
| `input` | — | 入口，提供输入事实作为初始上下文 |
| `output` | — | 出口，把当前累积上下文收集为最终输出 |
| `decisionTable` | `table`（内嵌决策表） | 对当前上下文求值决策表，输出并入上下文 |
| `expression` | `mappings[]`（`{key, expression}`） | 用 FEEL 表达式算出新字段，并入上下文 |
| `decision` | `decisionKey`（引用另一决策的 key） | 递归求值子决策，输出并入上下文 |

**边 GraphEdge**：`{ source, target }`，表示数据通路（source 节点输出流入 target）。

**求值语义：**

1. Kahn 拓扑排序（有环 → 失败归因 `决策图存在环`）。
2. 起始上下文 = 输入事实对象。
3. 按拓扑序逐节点求值，各节点输出**对象合并**（同名字段覆盖）进累积上下文。
4. `output` 节点把当前上下文快照为最终输出。
5. 子决策嵌套深度上限 **8**（超出 → `子决策嵌套过深（可能存在循环引用）`）。

**结构校验（`validate`）**：非空、节点 id 唯一、边端点存在、每个 `decisionTable` 节点必须带合法 `table`。

**子决策解析**：求值前，app 层用 **BFS** 沿 `decision` 节点递归预加载所有被引用的子决策定义（上限 128 个，防引用炸裂），构造 `MapResolver` 传入引擎。

**trace 展开**：`decision` 节点会把子决策的逐节点 trace 并入主 trace，实现跨决策的可解释性穿透。

## 5. FEEL 表达式语言

FEEL（Friendly Enough Expression Language）是 DMN 标准表达式语言。本引擎自研 tokenizer + Pratt 解析器 + 求值器 + 内置函数库（离线环境无法拉 dsntk-rs），值模型用 `serde_json::Value`，数值用 f64。

有两处用到 FEEL，语义不同：

- **单元测试（unary test）**：决策表 `inputEntries`，判"当前列值是否满足"→ **布尔**。
- **完整表达式**：决策表 `outputEntries`、`expression` 节点 `mappings`、`/feel/expression` 端点 → **任意值**。

### 5.1 单元测试（unary test）语法

针对"当前输入列值"判真假。

| 形式 | 语法 | 示例 | 说明 |
|------|------|------|------|
| 通配 | `-` 或空串 | `-` | 恒真，该列不参与判定 |
| 大于 | `> 数值` | `> 700` | 该列值 > 操作数 |
| 大于等于 | `>= 数值` | `>= 18` | ≥ |
| 小于 | `< 数值` | `< 100` | < |
| 小于等于 | `<= 数值` | `<= 65` | ≤ |
| 等于 | `= 值` 或裸值 | `"vip"` / `= 5` | 等值测试（`=` 可省略） |
| 不等于 | `!= 值` | `!= 0` | 不等（**不参与空隙分析**） |
| 闭区间 | `[下界..上界]` | `[0..100]` | 含两端 |
| 半开区间 | `[下界..上界)` | `[18..65)` | 含下界、不含上界 |
| 开区间 | `(下界..上界)` | `(0..1)` | 不含两端 |
| 反括号开区间 | `]a..b]` | `]1..5]` | ≡ `(1..5]` |
| 枚举（OR） | `值1, 值2, …` | `"north","south"` | 任一相等即命中 |
| 混合枚举 | 逗号分隔任意测试 | `> 100, < 0` | 任一真即真 |
| 否定 | `not(测试)` | `not(> 100)` | 对内部取反（**不参与空隙分析**） |
| 布尔 | `true` / `false` | `true` | 布尔字面量 |
| 空值 | `null` | `null` | null 字面量 |

**高级：引用其它变量 / 当前值 `?`**

比较操作数是完整 FEEL 表达式，可引用**其它输入变量**：

```
> avgScore          # 该列值 > 输入事实里的 avgScore 字段
```

裸布尔表达式里用 `?` 绑定**当前列值**：

```
contains(?, "vip")  # 当前列值包含子串 "vip"
? in [18..65)       # 当前列值在区间内
```

**类型容错**：null 值做序比较 → false（不报错，供缺失字段判 falsy）；类型不匹配的等值测试按 JSON 相等。

### 5.2 完整 FEEL 表达式

用于输出格、`expression` 节点、`/feel/expression`。

| 类别 | 语法 | 示例 | 结果 |
|------|------|------|------|
| 字面量 | 数字/字符串/布尔/null/列表 | `[1, 2, 3]` | `[1,2,3]` |
| 变量与路径 | `字段` / `对象.字段` | `order.amount` | 从 ctx 取值 |
| 算术 | `+ - * / **`，一元 `-` | `2 + 3 * 4` | `14`（`**` 右结合幂） |
| 字符串拼接 | `+` 重载 | `"tier-" + level` | `"tier-gold"` |
| 比较 | `< <= > >= = !=` | `score > 600` | `true` |
| 逻辑 | `and` / `or` / `not` | `a and b` | 布尔 |
| 条件 | `if…then…else` | `if score>=700 then "A" else "B"` | 分支值 |
| 成员 | `x in [1..10]` / `x in list` | `5 in [1..10]` | `true` |
| for 推导 | `for x in l return e` | `for x in [1,2,3] return x*10` | `[10,20,30]` |
| some 量词 | `some x in l satisfies c` | `some x in [1,2,3] satisfies x>2` | `true` |
| every 量词 | `every x in l satisfies c` | `every x in [1,2,3] satisfies x>0` | `true` |
| 列表过滤 | `l[cond]`（`item` 绑元素） | `[1,2,3,4][item > 2]` | `[3,4]` |
| 函数调用 | `fn(参数…)` | `max(1, 9, 4)` | `9` |

**运算符优先级**（低→高）：`or` < `and` < 比较 < `+ -` < `* /` < `**`（右结合）< 一元 `-`。

**除零**：`10 / 0` → `null`（不报错）。

## 6. 求值与 trace（可解释性）

**trace（`EvalResult.trace`）** 是逐节点求值轨迹数组，每个 `TraceNode`：

```jsonc
{
  "nodeId": "decisionTable",     // 节点 id（单表用 "decisionTable"，图节点用其 id）
  "nodeKind": "decisionTable",   // 节点类型：decisionTable / input / output / expression / decision / graph
  "matchedRules": [0],           // 命中的规则行号（0-based；多命中/聚合可多个；无命中为空）

  "input": { … },                // 进入该节点时的输入快照
  "output": { … },               // 该节点产出
  "timingUs": 0,                 // 求值耗时（微秒）
  "failure": null                // 失败归因；null=成功
}
```

> `matchedRules` 记录**所有满足条件的规则行**（0-based），即便命中策略（如 `F`/`U`）最终只选其一。例如 First 策略下若行 0 与行 2 都满足，`matchedRules` 为 `[0, 2]`，而输出取行 0。

**失败归因（超越 ZEN 的核心）**：任一单元格表达式解析/求值出错，`failure` 精确记明"哪条规则、哪个输入列、什么错"，而非静默吞掉或只抛顶层错。例如：

- UNIQUE 重叠：`命中策略 UNIQUE 违反：规则行 [0, 1] 同时命中（存在重叠）`
- 单元格出错：`规则行 2 求值失败: 输入列 "score" 单测 "> abc" —— …`
- 图有环：`决策图存在环`
- 子决策缺失：`子决策未找到: risk_score`

`options.trace=false` 可关闭 trace 返回（默认 true）。求值响应顶层若有任一节点失败，附加 `data.failure` 字段。

## 7. 完整性分析 gap / overlap

对决策表做**区域推理**，检出两类质量问题。对标 OpenL `validateDT`，超越 ZEN。

**overlap（重叠）**：两两规则，若**每一输入列**的结构化约束都相交，则可能同时命中。UNIQUE 策略下即冲突。

**gap（空隙）**：把每列按约束边界分段 → 各列代表点做**笛卡尔积** → 逐组合用**真实求值器**验证是否被任一规则覆盖，未覆盖即空隙。

**报告结构（`POST /decisions/{key}/analyze` 响应 data）：**

```jsonc
{
  "complete": true,          // 是否无空隙
  "hasOverlap": false,       // 是否有重叠
  "gaps":     [ { "description": "输入组合 score=680 & region=east 未被任何规则覆盖" } ],
  "overlaps": [ { "rules": [0, 1], "description": "规则行 0 与 1 可能同时命中（重叠）" } ]
}
```

**边界与保守处理：**

- 含 `not()` / `!=` 等无法结构化的单元格 → 跳过 gap 分析并显式说明（不静默）。
- 输入组合数超 **20000** → 跳过 gap 分析，提示"决策表过大，建议拆分"。
- gap 展示上限，超出附"另有 N 处未覆盖组合（已截断展示）"。
- 决策图：聚合各 `decisionTable` 节点的 gap/overlap，描述前缀 `[节点id]` 区分。

## 8. HTTP API 完整参考

**基址前缀**：所有端点挂在 `/api` 下，有两套等价前缀：

- **v1 正式契约**：`/api/rules/v1/*`（推荐）
- **旧前缀**（内嵌壳兼容）：`/api/rules/*`

下表路径省略 `/api/rules/v1` 前缀。所有响应为 `{code, msg, data}` 信封（详见 §9）。

### 定义管理

| 方法 | 路径 | 作用 | 请求体 | data 返回 |
|------|------|------|--------|-----------|
| GET | `/definitions` | 决策定义列表（元数据，不含决策体） | — | `[{key,name,version,published,updatedAt}]` |
| GET | `/definitions/{key}` | 决策详情（激活发布版或草稿） | — | 完整 `DecisionDef` |
| POST | `/definitions/draft` | 存草稿（结构校验后 upsert） | `DecisionDef` | `{key, saved:true}` |
| POST | `/definitions/validate` | 结构校验（不落库） | `DecisionDef` | `{valid:true}` 或 `{valid:false, error}` |
| DELETE | `/definitions/{key}` | 彻底删除（连带清理发布/日志/用例四表） | — | `{key, deleted:true}`；不存在→404 |

### 发布与版本

| 方法 | 路径 | 作用 | data 返回 |
|------|------|------|-----------|
| POST | `/definitions/{key}/publish` | 发布当前草稿 → 不可变 release + version+1 | `{key, version, published:true}` |

| POST | `/definitions/{key}/versions/{version}/activate` | 激活某版本 | `{key, version, active:true}` |

`ReleaseMeta`：`{id, key, version, rev, active, publishedBy, publishedAt}`（`rev` = 决策体内容哈希 xxhash64→16hex）。

### 求值

| 方法 | 路径 | 作用 | 落日志 |
|------|------|------|--------|
| POST | `/decisions/{key}/evaluate` | 按 key 装载定义并求值 | 是（默认） |
| POST | `/evaluate` | 内联定义求值（试算，需 body 带 `definition`） | 否 |
| POST | `/decisions/{key}/simulate` | 按 key 求值但**不落审计日志**（设计期试算） | 否 |

```jsonc

  "definition": { /* DecisionDef */ },          // 可选。内联定义（给定则优先于按 key 装载）
  "options": {
    "trace": true,   // 可选。是否返回 trace，默认 true
    "log": true      // 可选。是否落决策日志，默认 true
  }
}
```

**求值响应 data：** `{ output, logId, timingUs, trace?, failure? }`

### 完整性分析

| 方法 | 路径 | 作用 | 请求体 |
|------|------|------|--------|
| POST | `/decisions/{key}/analyze` | gap/overlap 完整性分析 | `{definition?}`（可传内联定义分析在编未存表；缺则按 key 装载） |

## 9. 响应信封与错误码

所有 API 返回统一信封（camelCase，字节对齐 cmx-api-types）：

```jsonc
{
  "code": 0,          // 0 = 成功；非 0 = 错误
  "msg": "success",   // 提示信息
  "data": { … }       // 成功时的数据；错误时省略
}
```

**错误码与 HTTP 状态映射（`RuleError`）：**

| 错误类型 | HTTP 状态 | code | 场景 |
|----------|-----------|------|------|
| Business 业务错误 | 200 | 1 | 定义非法、发布失败、表达式错误等 |
| NotFound 资源不存在 | 404 | 4 | 决策/日志/用例不存在 |
| Internal 内部错误 | 500 | 5 | DB 查询失败等 |
| Unauthorized 未认证 | 401 | 401 | jwt/apikey 模式下缺/坏令牌 |

> 注意：**业务错误走 HTTP 200 + code=1**（前端按 `code` 判成败，非 HTTP 状态）。`校验类`端点（validate、feel/validate）即使校验不通过也返回 200 + code=0，用 `data.valid` 表达结果。

## 11. 认证与多租户

### 认证模式（`auth.mode`，toml `[auth]` 段；env 覆盖 `AUTH__MODE`）

| 模式 | 说明 |
|------|------|
| `off`（默认） | 不校验，建 `default` 租户 scope 放行 —— 单租户零回归 |
| `jwt` | 验 Bearer JWT（HS256），解 tenant/user/roles claim；缺/坏 → 401 |
| `apikey` | 验 `X-Api-Key` 头，命中绑定租户免 JWT |

**JWT claim 映射**（可配）：`sub`→user；`auth.jwt_tenant_claim`（默认 tenant）→租户；`auth.jwt_roles_claim`→角色数组。R0 不强制过期校验。

### 多租户（`auth.tenancy`；multi 的库 URL 模板仍走 env `RULE_TENANT_DB_URL_TEMPLATE`）

| 模式 | 说明 |
|------|------|
| `single`（默认） | 单库，恒用 `rule_pg`（`RULE_DB_ID`），零回归 |
| `multi` | **db-per-tenant 物理隔离**：按租户派生库 `rule_<tenant>`（小写），懒注册数据源 + 建表 |

`multi` 模式下，库 URL 由 `RULE_TENANT_DB_URL_TEMPLATE` 的 `{tenant}` 占位派生，每个 db_id 首次访问时懒建（数据源注册 + DDL）。库即租户边界，表内不带 tenant 列。

数据源统一走 toml `[[databases]]` 段（db_id=`rule_pg`，default=true；**缺段启动失败**，旧 `RULE_PG_URL` 已废弃）。

配置也可写 `rules-server.toml` 的 `[auth]` / `[datasource]` 段（env 优先于 toml）。

### 特性

- **无 poller**：纯请求驱动，无后台轮询。
- **chassis 装配**：分层日志、中间件栈、启动钩子、SIGTERM 优雅关闭、渐变 banner。
- 端口选择避开平台 8080 / flow 8091 / report 8092。

## 13. 数据库表结构

四张表，`cmx_rule_` 前缀，**无外键**（用索引替代），DDL 幂等。multi 模式下 per-tenant DB 隔离，表内不带 tenant 列。

**`cmx_rule_definition`（决策定义 · 草稿态）：**

| 列 | 类型 | 说明 |
|----|------|------|
| `key` | VARCHAR(128) PK | 业务键 |
| `name` | VARCHAR(256) | 展示名 |
| `version` | INTEGER | 当前版本 |
| `published` | BOOLEAN | 是否已发布 |
| `body` | JSONB | 决策体 IR（含 kind 标签） |
| `created_at` / `updated_at` | TIMESTAMPTZ | 时间戳 |

**`cmx_rule_release`（不可变发布）：** `id` PK / `key` / `version` / `rev`（内容哈希）/ `body`（发布快照）/ `active` / `published_by` / `published_at`。唯一索引 `(key, version)`。

**`cmx_rule_decision_log`（决策日志/审计）：** `id` PK / `decision_key` / `decision_version` / `input` / `output` / `trace`（JSONB）/ `timing_us` / `caller` / `failure`（非空=失败）/ `created_at`。

**`cmx_rule_test_case`（测试用例）：** `id` PK / `decision_key` / `name` / `input` / `expected` / `created_at`。

> 无 RU（运行时）表 —— 规则决策无长驻状态，纯函数式求值。

## 15. FAQ / 已知偏差

**Q：数值为什么是 f64 而非严格 Decimal128？**
A：R1 FEEL 引擎自研（离线无法拉 dsntk-rs），值模型复用 `serde_json::Value`，数值统一 f64。这是 R1 已知偏差；金额精度敏感场景需注意浮点。输出中整数会显示为 `50000.0` 形态。

**Q：P（优先）/ O（输出序）策略为什么退化成取首行？**
A：R0/R1 未完善优先级列表，暂退化为行序取首个；后续里程碑补齐。

**Q：`not()` / `!=` 为什么不参与空隙分析？**
A：补集难以可靠结构化，分析保守跳过并显式告知（不静默漏报）。

**Q：草稿没发布能求值吗？**
A：能。装载优先取激活发布版，无发布则回退草稿，故设计期可直接 evaluate/simulate 试算。

**Q：改了前端 `.js` 要重启吗？**
A：不用。native 页每请求从磁盘 live 读。改**后端 Rust** 才需重启 rules-server。

**Q：v1 和旧前缀有何区别？**
A：功能完全一致。`/api/rules/v1/*` 是正式契约（推荐），`/api/rules/*` 是内嵌壳兼容前缀，两者都活。

**Q：业务错误为什么返回 HTTP 200？**
A：本引擎按 `code` 字段判成败（0=成功），业务错误走 200+code=1，仅 NotFound(404)/Internal(500)/Unauthorized(401) 用 HTTP 状态。前端应读 `code` 而非 HTTP 状态。
