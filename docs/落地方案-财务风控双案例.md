> 所有决策定义与求值结果均在运行的 cmx-rulesengine（`:8094`）上**逐条实测通过**，可照抄。
> 配合 [`使用手册.md`](使用手册.md) 阅读。

## 1. 为什么这两个案例

| 案例 | 展示的核心能力 | 集团痛点 |
|------|--------------|---------|
| 费用报销 | **决策图**编排 + **子决策复用** + **expression 计算** + 记账推导 | 差旅标准年年调、各子公司制度不一、报销科目易错 |
| 反洗钱 | **Collect 多命中** + 风险评分 + **完整性分析** | 监管规则频繁变、需一次性列出所有触发原因、合规审计要留痕 |

两个案例合起来覆盖了规则引擎在集团里的四大价值面：**业务自维护、多规则编排、质量可验证（gap/overlap）、决策可追溯（trace + 日志）**。

## 2. 案例一：费用报销智能处理

### 2.1 业务背景与痛点

集团员工提交费用报销单，系统需自动判定：**是否超标 → 需要什么级别审批 → 记什么会计科目**。

传统硬编码方式的问题：
- 差旅标准（职级 × 城市档 → 住宿上限）**每年调整**，改一次要发版；
- 各子公司标准不同，代码里堆满 `if-else`；
- 费用类别 → 会计科目的映射，财务改科目表要找 IT。

**规则引擎方案**：把三段逻辑拆成 3 个决策，财务人员在设计器里自维护。

### 2.2 决策拆解与建模

```
                          费用报销单 (input)
                        {level, cityTier, category, amount}
                                  │
        ┌─────────────────────────┼──────────────────────────┐
        ▼                                                     
  ┌───────────────┐                                           
  │ travel_standard│ 子决策·决策表(F)                          
  │ 差旅住宿标准    │ 职级×城市档 → hotelCap                    
  └───────┬───────┘                                           
          │ hotelCap 并入上下文                                
          ▼                                                    
  ┌───────────────┐                                           
  │ chk 超标与审批 │ expression 节点                           
  │ 判定           │ isOverLimit / approvalLevel               
  └───────┬───────┘                                           
          │                                                    
          ▼                                                    
  ┌───────────────┐                                           
  │ expense_account│ 子决策·决策表(F)                          
  │ 费用记账科目    │ category → debit 科目                     
  └───────┬───────┘                                           
          ▼                                                    
     处理结论 (output)
  {hotelCap, isOverLimit, approvalLevel, debit, debitName}
```

**为什么拆 3 个而不是 1 张大表？**
- `travel_standard`（差旅标准）和 `expense_account`（记账科目）是**可独立复用的原子决策**——差旅标准还能被"预订审批""预算控制"复用，记账科目能被"预付冲销""总账"复用。
- 主图 `expense_claim` 只负责**编排**，逻辑清晰、各子决策可独立维护和测试。

### 2.3 完整定义（3 个决策，可直接建）

**① 子决策：差旅住宿标准 `travel_standard`**（决策表，First 策略）

```bash
curl -XPOST http://127.0.0.1:8094/api/rules/v1/definitions/draft \
  -H 'Content-Type: application/json' -d '{
  "key": "travel_standard", "name": "差旅住宿标准", "kind": "decisionTable", "hitPolicy": "F",
  "inputs": [
    { "id":"i1", "label":"职级",     "expression":"level" },
    { "id":"i2", "label":"城市级别", "expression":"cityTier" }
  ],
  "outputs": [ { "id":"o1", "name":"hotelCap", "label":"住宿上限" } ],
  "rules": [
    { "inputEntries":[">= 5",     "-"],        "outputEntries":["1000"], "annotation":"高管不分城市" },
    { "inputEntries":["[3..5)",   "\"tier1\""], "outputEntries":["800"],  "annotation":"中层·一线城市" },
    { "inputEntries":["[3..5)",   "-"],        "outputEntries":["500"],  "annotation":"中层·其他城市" },
    { "inputEntries":["< 3",      "\"tier1\""], "outputEntries":["500"],  "annotation":"员工·一线城市" },
    { "inputEntries":["< 3",      "-"],        "outputEntries":["300"],  "annotation":"员工·其他城市" }
  ]
}'
```

> **策略选型**：这里用 **F（First）** 而非 U（Unique）。因为"一线城市行"和"其他城市通配行"对同一职级会**同时命中**（`tier1` 也满足通配 `-`），用 U 会判为冲突报错。First 按行序取第一个匹配——把**更具体的规则排在前**，通配兜底排在后，是决策表的经典写法。详见 [2.5 节踩坑](#25-建模要点一个真实踩过的坑)。

**② 子决策：费用记账科目 `expense_account`**（决策表，First 策略）

```bash
curl -XPOST http://127.0.0.1:8094/api/rules/v1/definitions/draft \
  -H 'Content-Type: application/json' -d '{
  "key": "expense_account", "name": "费用记账科目", "kind": "decisionTable", "hitPolicy": "F",
  "inputs":  [ { "id":"i1", "label":"费用类别", "expression":"category" } ],
  "outputs": [
    { "id":"o1", "name":"debit",     "label":"借方科目" },
    { "id":"o2", "name":"debitName", "label":"科目名称" }
  ],
  "rules": [
    { "inputEntries":["\"travel\""], "outputEntries":["\"660101\"", "\"差旅费\""] },
    { "inputEntries":["\"office\""], "outputEntries":["\"660102\"", "\"办公费\""] },
    { "inputEntries":["\"meal\""],   "outputEntries":["\"660103\"", "\"业务招待费\""] },
    { "inputEntries":["-"],          "outputEntries":["\"660199\"", "\"其他费用\""], "annotation":"兜底" }
  ]
}'
```

**③ 主决策图：费用报销智能处理 `expense_claim`**

```bash
curl -XPOST http://127.0.0.1:8094/api/rules/v1/definitions/draft \
  -H 'Content-Type: application/json' -d '{
  "key": "expense_claim", "name": "费用报销智能处理", "kind": "graph",
  "nodes": [
    { "id":"in",  "name":"报销单", "type":"input" },
    { "id":"std", "name":"差旅标准", "type":"decision", "decisionKey":"travel_standard" },
    { "id":"chk", "name":"超标与审批判定", "type":"expression", "mappings":[
      { "key":"isOverLimit",  "expression":"if category = \"travel\" then amount > hotelCap else false" },
      { "key":"approvalLevel", "expression":"if category = \"travel\" and amount > hotelCap then \"manager\" else if amount > 2000 then \"manager\" else \"auto\"" }
    ]},
    { "id":"acc", "name":"记账科目", "type":"decision", "decisionKey":"expense_account" },
    { "id":"out", "name":"处理结论", "type":"output" }
  ],
  "edges": [
    { "source":"in",  "target":"std" },
    { "source":"std", "target":"chk" },
    { "source":"chk", "target":"acc" },
    { "source":"acc", "target":"out" }
  ]
}'
```

**审批判定逻辑（chk 节点）**：
- `isOverLimit`：仅**差旅类**才拿金额比住宿上限（`if category = "travel" then amount > hotelCap else false`）——非差旅费用不受住宿标准约束。
- `approvalLevel`：差旅超标 → `manager`；或任意类别金额 > 2000 → `manager`；否则 `auto`（自动通过）。

### 2.4 求值验证（4 个场景实测）

| # | 场景 | 输入 | 输出（实测） |
|---|------|------|-------------|
| 1 | 差旅超标 | `{level:4, cityTier:"tier1", category:"travel", amount:900}` | `hotelCap:800, isOverLimit:true, approvalLevel:"manager", debit:"660101"(差旅费)` |
| 2 | 差旅达标 | `{level:4, cityTier:"tier1", category:"travel", amount:700}` | `hotelCap:800, isOverLimit:false, approvalLevel:"auto", debit:"660101"` |

| 4 | 招待小额 | `{level:2, cityTier:"tier3", category:"meal", amount:300}` | `approvalLevel:"auto", debit:"660103"(业务招待费)` |

**trace 就是审计凭据**：住宿标准命中行 1（中层·一线→800）、900>800 判超标、需 manager 审批、记 660101 差旅费——每一步都可还原。

### 2.5 建模要点：一个真实踩过的坑

**第一版 `travel_standard` 用 U（Unique）策略结果求值失败**，这是决策表建模最常见的错误，值得记录：

```
输入 {level:4, cityTier:"tier1"}：
  规则行 1: [3..5) + "tier1"  → 命中 ✓
  规则行 2: [3..5) + "-"(通配) → 也命中 ✓   ← 两行同时命中！
```

U 策略要求**至多一行命中**，两行命中直接失败归因：

```
failure: "命中策略 UNIQUE 违反：规则行 [1, 2] 同时命中（存在重叠）"
```

而 `hotelCap` 变成 `null`，导致下游超标判定全部失效。

**如何提前发现？** 用 `analyze` 端点做完整性分析（**这正是超越 ZEN 的能力**）：

```bash
curl -XPOST http://127.0.0.1:8094/api/rules/v1/decisions/travel_standard/analyze -d '{}'
# U 版返回：{ "hasOverlap": true, "overlaps": [{"rules":[1,2], "description":"规则行 1 与 2 可能同时命中（重叠）"}] }
```

**两种正确解法：**

| 解法 | 做法 | 适用 |
|------|------|------|
| 改 **F（First）** | 具体规则排前、通配兜底排后，取首个命中 | 有明确优先级（推荐，本案例用此） |
| 保持 **U**，消除重叠 | 把通配行改成互斥条件（如 `not("tier1")`） | 要求规则严格不重叠、便于审计 |

**教训**：决策表设计完，**上线前必跑 `analyze`**。gap（空隙，有输入无规则覆盖）和 overlap（重叠，多规则冲突）是规则质量的两大杀手，人工检查几乎必漏。

## 3. 案例二：反洗钱交易预警

### 3.1 业务背景

金融/财务场景下，每笔交易需实时筛查多条反洗钱（AML）规则，**一笔可疑交易往往同时触发多个规则**（如既是大额、又涉高风险国、又是高风险客户）。监管要求：
- **列出所有触发的规则**（不能只报一条）；
- 累计风险分，超阈值转人工核查；
- 每次筛查留痕，供监管核查。

这正是 **Collect（收集）命中策略**的舞台。

### 3.2 完整定义与实测

**决策表 `aml_screening`（Collect 策略）：**

```bash
curl -XPOST http://127.0.0.1:8094/api/rules/v1/definitions/draft \
  -H 'Content-Type: application/json' -d '{
  "key": "aml_screening", "name": "反洗钱交易预警", "kind": "decisionTable", "hitPolicy": "C",
  "inputs": [
    { "id":"i1", "label":"单笔金额",     "expression":"amount" },
    { "id":"i2", "label":"当日累计",     "expression":"dailyTotal" },
    { "id":"i3", "label":"对手方高风险国", "expression":"counterpartyRisk" },
    { "id":"i4", "label":"客户风险等级",  "expression":"customerRisk" }
  ],
  "outputs": [
    { "id":"o1", "name":"rule",  "label":"命中规则" },
    { "id":"o2", "name":"score", "label":"风险分" }
  ],
  "rules": [
    { "inputEntries":[">= 50000",     "-",         "-",    "-"],       "outputEntries":["\"大额交易\"",   "30"] },
    { "inputEntries":["-",            ">= 200000", "-",    "-"],       "outputEntries":["\"当日累计超限\"", "40"] },
    { "inputEntries":["-",            "-",         "true", "-"],       "outputEntries":["\"涉高风险国\"",   "50"] },
    { "inputEntries":["-",            "-",         "-",    "\"high\""], "outputEntries":["\"高风险客户\"",   "35"] },
    { "inputEntries":["[9000..10000)","-",         "-",    "-"],       "outputEntries":["\"疑似拆分规避\"", "45"] }
  ]
}'
```

**求值验证（实测）：**

**场景 A｜多命中**（6 万单笔 + 25 万累计 + 高风险国 + high 客户）：

```bash
curl -XPOST http://127.0.0.1:8094/api/rules/v1/decisions/aml_screening/evaluate \
  -H 'Content-Type: application/json' \
  -d '{"input":{"amount":60000,"dailyTotal":250000,"counterpartyRisk":true,"customerRisk":"high"}}'
```

输出——**一次收集全部 4 条命中规则**（命中行 `[0,1,2,3]`）：

```json
{ "code":0, "data": { "output": [
  { "rule":"大额交易",     "score":30.0 },
  { "rule":"当日累计超限", "score":40.0 },
  { "rule":"涉高风险国",   "score":50.0 },
  { "rule":"高风险客户",   "score":35.0 }
] } }
```

**场景 B｜疑似拆分**（9500 元，卡在 9000~10000 规避 1 万申报线）：

```json
{ "output": [ { "rule":"疑似拆分规避", "score":45.0 } ] }
```

**场景 C｜正常交易**（3000 元 / 低风险）→ 无命中，返回**空数组** `[]`（= 无预警放行）。

### 3.3 C / C+ / C# 策略选型

同一张 AML 表，换命中策略得到不同粒度的结果：

| 策略 | 输出（场景 A） | 用途 |
|------|--------------|------|
| `C`（Collect） | 全部命中明细数组 `[{rule,score}×4]` | **列出所有触发原因**（监管留痕、人工核查） |
| `C+`（求和） | `80.0`（单输出列求和） | 累计风险总分，比阈值决定是否拦截 |
| `C#`（计数） | `4` | 命中规则数，快速分流 |

> **实测**：把上表输出改成单列 `score`、策略改 `C+`，输入 `{amount:60000, counterpartyRisk:true}` → 求和 `80.0`（30+50）。生产中常**同时部署两张表**：`C` 表出明细给审计，`C+` 表出总分给风控引擎判拦截。

**典型编排**（决策图）：`AML明细(C) → 风险总分(C+) → 处置决策表(总分→放行/复核/拦截)`。

## 4. 与流程引擎（cmx-flowengine）集成

规则引擎算"**该怎么判**"，流程引擎管"**流转到谁**"。费用报销的完整闭环：

```
员工提交报销单
      │
      ▼
[cmx-flowengine 流程实例启动]
      │  ServiceTask 节点调用规则引擎
      ▼
POST /api/rules/v1/decisions/expense_claim/evaluate
      │  返回 {approvalLevel, isOverLimit, debit, ...}
      ▼
[流程按 approvalLevel 路由]
   approvalLevel="auto"    → 自动通过，直接记账
   approvalLevel="manager" → 转经理审批任务
      │
      ▼
[审批通过 → 调 fico 记账，用规则算出的 debit 科目]
```

**集成方式**：cmx-flowengine 的 ServiceTask（HttpDelegate）POST 到规则引擎的 evaluate 端点，把 `output` 合并回流程变量，网关节点按 `approvalLevel` 分支。两个引擎都是独立微服务，通过 HTTP 契约解耦。

**职责边界**：

| 引擎 | 负责 | 不负责 |
|------|------|-------|
| 规则引擎 | 超标判定、审批级别计算、科目推导 | 谁审批、审批顺序、催办 |
| 流程引擎 | 任务分派、审批流转、会签抄送 | 业务判定逻辑 |

## 5. 与财务记账（fico/GL）集成

规则引擎的 `expense_account` 子决策直接产出**记账所需的科目**，对接你的 GL 平台：

```
报销审批通过
    │
    ▼
规则输出 {debit:"660101", debitName:"差旅费", amount:900}
    │
    ▼
生成记账凭证（通用日记账 ga_journal）：
    借：660101 差旅费        900
      贷：100201 银行存款    900
```

**进阶**：把整个"科目推导 + 借贷方向 + 辅助核算维度"都做成决策图，实现**智能记账引擎**——业务类型 × 组织 × 往来对象 → 完整分录。财务制度变更时改决策表，不动记账代码。这也是规则引擎在集团财务的最大价值点。

## 6. 上线 Checklist

每个决策上线前，按此清单验证：

- [ ] **结构校验**：`POST /definitions/validate` 返回 `valid:true`。
- [ ] **完整性分析**：`POST /decisions/{key}/analyze` —— 检查 `hasOverlap` 和 `complete`。
  - 有 overlap？确认是否 U 策略误用（改 F 或消除重叠）。
  - 有 gap？确认是否漏了输入组合（补规则或加通配兜底行）。
- [ ] **测试用例回归**：为关键场景建 test case，`POST /decisions/{key}/tests/run` 全通过（含边界值）。
