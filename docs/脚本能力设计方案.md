# cmx-rulesengine · 脚本能力设计方案

> 为决策引擎补齐**脚本（Script）能力**——让规则作者在 FEEL 表达式之外，用一门**通用脚本语言**表达复杂过程逻辑（多语句、局部变量、循环、分支、自定义函数）。
>
> **本文档只做方案设计，不动代码。** 版本 v1 · 2026-08-18
> 配合 [`cmx-rulesengine-design.md`](cmx-rulesengine-design.md)（总设计）与 [`使用手册.md`](使用手册.md) 阅读。
>
> **结论先行**：脚本引擎选 **Rhai**（设计文档 §10 早已钦定的"脚本逃生舱"，MIT/Apache、Don't-Panic 保证、可沙箱、可 WASM，且 `rhai-1.20.0` **已在离线缓存**）。脚本以**四种载体**分层落地：决策图 **Script 节点**（P0）→ 决策表**脚本单元格**（P1）→ 可复用**脚本函数库**（P2）→ **脚本化子决策**（P3）。全部围绕**唯一表达式求值接缝** `cmx_rule_feel::eval_output` 展开，对现有决策表/决策图求值路径**零破坏、纯增量**。

## 1. 为什么要脚本能力

现有引擎有两套表达式，都是**单表达式求值**（一个式子算一个值）：

- **决策表 unary test**（`inputEntries`）：`> 700` / `[18..65)` / `"north","south"`
- **完整 FEEL 表达式**（`outputEntries`、`expression` 节点、`/feel/expression`）：`income * 5` / `if score>700 then "A" else "B"`

FEEL 覆盖了绝大多数"判定 + 简单计算"，但集团级复杂决策里，总有一类逻辑**FEEL 表达不动或表达得很别扭**：

| 场景 | 为什么 FEEL 吃力 |
|------|------------------|
| 阶梯累进计算（个税、阶梯电价、阶梯佣金） | 需要循环累加 + 多个局部变量暂存中间量 |
| 多步骤过程（先算基数→再套系数→再封顶→再取整） | FEEL 单表达式要嵌套成一长串，不可读、难维护 |
| 复杂字符串处理（解析、拼装报文、格式化） | FEEL 内置函数有限，无正则、无 split/join 组合 |
| 带状态的迭代（对明细行逐条累计判定） | FEEL 的 `for` 是纯函数推导，不能带可变累加器 |
| 业务专家习惯的"伪代码式"表达 | `if/else` 多分支 + 变量赋值，脚本比嵌套 FEEL 直观 |

**脚本能力 = 给规则作者一个"过程式逃生舱"**：当声明式的决策表/FEEL 不够用时，用一段**受控、沙箱、可审计**的脚本兜底——但**不取代**决策表/FEEL，而是与之**分层共存**。

> 这正是 GoRules ZEN 的 **Function 节点**（内嵌 JS 经 QuickJS）、Drools 的 **RHS action**、IBM ODM 的 **BAL action** 在做的事。本方案用 Rhai 替代 JS（Rust 原生、无需嵌 JS 运行时、沙箱更可控）。

## 2. FEEL vs 脚本：边界与分工

**核心原则：能用 FEEL 就用 FEEL，FEEL 不够才用脚本。** 二者分工：

| 维度 | FEEL 表达式 | Rhai 脚本 |
|------|------------|-----------|
| 形态 | 单表达式（一个式子 → 一个值） | 多语句块（可 `let`/`for`/`if`/`return`） |
| 定位 | 决策**判定** + 简单计算 | 复杂**过程**计算 + 数据变换 |
| 标准 | DMN 标准，跨工具链互通 | 通用脚本，本引擎内 |
| 可读性（业务） | 高（声明式、贴近自然语言） | 中（需一点编程基础） |
| 完整性分析 | ✅ 参与 gap/overlap | ❌ 不参与（黑盒，见 §9） |
| 沙箱风险 | 极低（受控 AST，无副作用） | 低（Rhai 沙箱 + 操作数/深度/超时限制） |
| 典型用途 | 决策表单元格、字段变换、条件 | Script 节点、阶梯计算、多步过程 |

**决策树（规则作者视角）：**

```
要表达一段逻辑
   │
   ├── 是"判定"（值满足某条件）？ ──→ 决策表 unary test
   │
   ├── 是"单步计算"（一个式子出结果）？ ──→ FEEL 表达式
   │
   └── 是"多步过程 / 循环 / 复杂变换"？ ──→ Rhai 脚本
```

## 3. 选型：为什么是 Rhai

设计文档 §10 早已把 **Rhai** 列为"Function 节点脚本逃生舱"的选型，本方案确认之。四引擎横评：

| 引擎 | 许可 | 离线缓存 | 沙箱 | 嵌入成本 | 结论 |
|------|------|---------|------|---------|------|
| **Rhai 1.20** | MIT/Apache | ✅ **已缓存** | 操作数/调用深度/超时/无 std 泄漏 | Rust 原生、类型与 `serde_json` 易桥接 | **选它** |
| CEL (cel-interpreter) | Apache | ❌ 未缓存（需联网，当前拉不到） | 天生无副作用 | 纯策略语言，无循环/局部变量 | 表达力不足，且离线不可用 |
| WASM (wasmtime 39) | Apache | ✅（平台已用） | 强隔离 | 作者需自备工具链编译 wasm、字节码不可读、调试难 | 对"业务人员写脚本"过重 |
| QuickJS (rquickjs) | MIT | ❌ 未缓存 | 需嵌 JS 运行时 | 引入完整 JS 引擎，体积/攻击面大 | 离线不可用，且违背"纯 Rust"取向 |

**Rhai 的关键优势（对本引擎）：**

1. **离线即用**：`rhai-1.20.0.crate` 已在本地 registry 缓存，无需联网。
2. **Don't-Panic 保证**：Rhai 官方承诺脚本永不 panic 宿主，错误以 `Result` 返回——完美契合引擎"永不 panic，失败落 trace 的 `failure`"纪律。
3. **沙箱原生**：内置 `max_operations`（操作数上限）、`max_call_levels`（调用深度）、`max_string_size`/`max_array_size`、`Engine::on_progress`（可插超时钩子）——不用自己造沙箱。
4. **类型易桥接**：Rhai 的 `Dynamic` 与 `serde_json::Value` 双向转换直接（`rhai::serde` feature）；引擎值模型本就是 `serde_json::Value`，零阻抗。
5. **纯 Rust、可 WASM**：与引擎"语义中立内核可 wasm 复用"纪律一致，将来前端浏览器内跑脚本预览也可行。
6. **语法亲民**：`let x = ...; if ... { ... } for i in ... { ... } x` ——业务人员比 FEEL 嵌套更易上手。

**务实边界**：Rhai 不追求 DMN 标准互通（那是 FEEL 的职责）。脚本是"本引擎内的过程逃生舱"，导出 DMN 时脚本节点降级为"外部函数引用"占位（见 §14）。

## 4. 架构接缝：ExprEngine 抽象

**关键洞察**：引擎里**所有表达式求值都收敛到唯一入口** `cmx_rule_feel::eval_output(src, ctx)`：

- 决策表输出格（`cmx-rule-engine/src/lib.rs:145`）
- 决策图 expression 节点（`cmx-rule-engine/src/graph.rs:92`）
- FEEL 端点 `/feel/expression`

这意味着**脚本能力不需要改求值主流程**，只需在这个接缝处**按语言分派**。设计一个薄抽象：

```
                    ┌─────────────────────────────────┐
   表达式源码 src ──▶│  eval_scripted(lang, src, ctx)   │
   语言标签 lang     │                                 │
                    │   match lang {                  │
                    │     "feel"|"" => 现有 FEEL 引擎   │  ← 默认，零回归
                    │     "rhai"    => Rhai 沙箱求值    │  ← 新增
                    │   }                             │
                    └─────────────────────────────────┘
```

**落点**：`cmx-rule-feel` crate 新增 `script.rs` 模块，暴露 `eval_script(src, ctx) -> Result<Value, FeelError>`（Rhai 求值 + serde 桥接 + 沙箱配置）。`eval_output` 增一个"带语言标签"的姊妹函数，或让调用点按节点的 `lang` 字段分派。**FEEL 引擎（expr.rs）一行不改。**

> 这与设计文档 §7「**把表达式层做成可替换 trait，别锁死**」的纪律一致——`ExprEngine` 就是那个 trait 的具体化：FEEL 与 Rhai 两个实现，按 `lang` 标签选择。

**依赖变更**：`cmx-rule-feel/Cargo.toml` 加 `rhai = { version = "1.20", features = ["serde", "sync"] }`（`sync` 保 `Send+Sync` 契合引擎；`serde` 保 `Dynamic ↔ Value` 桥接）。离线可解析（已缓存）。

## 5. 四种载体形态

四种载体覆盖"脚本在决策模型里怎么用"的全部场景，按落地优先级 P0→P3 排列（复杂度与依赖递进）。

### 5.1 P0 · 决策图 Script 节点

**最贴合现有架构**——`GraphNode` 已是扁平结构（`node_type` 字符串 + 类型专属可选字段），加一种 `script` 节点类型**零破坏**（现有 `other =>` 分支已兜底未知类型）。

**模型扩展**（`ir.rs` 的 `GraphNode` 加两个可选字段）：

```jsonc
{
  "id": "calc", "name": "阶梯个税计算", "type": "script",
  "lang": "rhai",                 // 新增：脚本语言，默认 "rhai"
  "script": "let t = 0.0;\nlet b = income;\nif b > 80000 { t += (b-80000)*0.45; b = 80000; }\nif b > 55000 { t += (b-55000)*0.35; b = 55000; }\n// …\n#{ tax: t, afterTax: income - t }"
}
```

**求值语义**（`graph.rs` 加 `"script" =>` 分支，与 `"expression"` 节点并列）：

1. 脚本以**当前累积上下文**为输入变量（同 expression 节点的 `node_ctx`）。
2. 脚本返回一个**对象**（Rhai 的 `#{...}` map），其字段**合并进累积上下文**（同 `merge`）。
3. 脚本出错 → 该节点 `failure` 归因（"脚本节点 calc 第 N 行：xxx"），永不 panic。
4. 产一个 `TraceNode`（`nodeKind: "script"`），记输入快照 + 输出 + 耗时。

**为什么这是 P0**：改动面最小（model 加 2 字段 + engine 加 1 个 match 分支 + feel 加 script.rs），与决策图的"节点编排"范式天然契合，且是 GoRules JDM Function 节点的直接对标。

### 5.2 P1 · 决策表脚本单元格

决策表的**输出格**（`outputEntries`）当前是 FEEL 表达式。允许某个输出格写脚本——**逐格逃生舱**。

**两种设计（择一，倾向 A）：**

**方案 A · 前缀标记**（零模型变更）：输出格文本以特定前缀标记为脚本，如 `=rhai:` 开头：

```jsonc
"outputEntries": ["\"A\"", "=rhai: let base=income*5; if vip { base*1.2 } else { base }"]
```

`eval_output` 在求值前 sniff 前缀：`=rhai:` → 走 Rhai；否则走 FEEL（默认）。**零 DDL、零模型字段、向后兼容**。

**方案 B · 结构化**（模型变更）：`DecisionRule` 加平行的 `outputLangs: ["feel", "rhai"]` 数组标注每格语言。更规整但需改 IR + 前端网格。

> **倾向方案 A**：前缀标记零破坏、渐进、前端设计器只需在 fx 向导加个"脚本"选项插入前缀。决策表本应保持"声明式为主"，脚本单元格是**少数逃生舱**，不值得为它改 IR 结构。

**约束**：脚本单元格**只影响该输出格的值**，不改判定（`inputEntries` 仍是 FEEL unary test，保持决策表"可分析"）。

### 5.3 P2 · 可复用脚本函数库

独立命名的脚本函数（如 `calcTax(income)`、`riskScore(age, credit)`），**决策表/决策图/其它脚本都能调用**——集中管理、跨决策复用。

**这是脚本能力的"杠杆放大器"**：把常用计算沉淀成函数库，规则里一句 `calcTax(income)` 调用，而非到处复制脚本。

**模型**（新增独立实体 `ScriptFunction`，不塞进 DecisionDef）：

```jsonc
{
  "name": "calcTax",
  "params": ["income", "deductions"],
  "lang": "rhai",
  "body": "let taxable = income - deductions;\n// 阶梯累进…\ntaxable * 0.2",
  "description": "个税阶梯计算",
  "version": 1
}
```

**注册与调用**：
- 求值前，引擎把租户的全部已发布函数注册进 Rhai `Engine`（`register_fn` 或 `Engine::compile` 成 `AST` 合并）。
- 决策里任意脚本/表达式即可 `calcTax(income, 5000)`。
- FEEL 表达式**也能调用**（`eval_output` 侧把函数库作为 FEEL 的 `FunctionProvider` 注入——对应设计文档 §8 预留的 `FunctionProvider` 扩展点）。

**存储**：新增第 5 张表 `cmx_rule_script_function`（`name` PK、`params` JSONB、`body` TEXT、`lang`、`version`、`published`、时间戳）。多租户下随租户库。

**为什么是 P2**：需要新存储 + 新管理端点 + 函数注册机制，依赖 P0 的 Rhai 接缝先就位。价值高（复用杠杆），但工程量比 P0/P1 大。

### 5.4 P3 · 脚本化子决策

整个决策体除 `decisionTable` / `graph` 外，**新增第三种 `kind: "script"`**——一个决策就是一段脚本，输入事实 → 输出。

**这是最纯粹的脚本决策**，对标"整个规则就是一段代码"。

**模型**（`DecisionBody` enum 加第三变体，与设计文档"R2 加 Graph 变体不破坏 R0"同纪律）：

```jsonc
{
  "key": "dynamic_pricing", "name": "动态定价", "version": 1,
  "kind": "script",              // 新第三类
  "lang": "rhai",
  "script": "let price = base_price;\nif demand > 0.8 { price *= 1.3; }\nif is_member { price *= 0.9; }\n#{ finalPrice: price, applied: demand > 0.8 }"
}
```

**求值语义**（`evaluate_with` 的 `match &def.body` 加 `Script` 臂）：脚本以输入事实为变量 → 返回对象即输出 → 产 1 个 `TraceNode`（`nodeKind: "script"`）。

**可被决策图 `decision` 节点引用**（脚本化子决策 = 图里一个 decision 节点指向它），也能被 `tests/run` 回归、被 evaluate 落日志——**完全融入现有生命周期**（发布/版本/审计/测试）。

**为什么是 P3**：是第四类决策体（DecisionBody 加变体），触及最多既有代码路径（validate/evaluate/analyze/前端预览/设计器），但因前三载体已把 Rhai 接缝、沙箱、trace 打磨成熟，P3 只是"把脚本提升为顶层决策体"，水到渠成。

## 6. 沙箱与安全

脚本是**受信租户内的业务逻辑**，但仍须沙箱化防"脚本写崩引擎 / 无限循环 / 资源耗尽"。Rhai 原生提供全部所需闸门：

| 风险 | Rhai 闸门 | 建议默认 |
|------|-----------|---------|
| 无限循环 / CPU 耗尽 | `Engine::set_max_operations(n)` | 100_000 操作 |
| 递归爆栈 | `Engine::set_max_call_levels(n)` | 32 层 |
| 内存爆炸 | `set_max_string_size` / `set_max_array_size` / `set_max_map_size` | 各 64KB / 10_000 / 10_000 |
| 挂起超时 | `Engine::on_progress(closure)` 按操作计数检查 wall-clock | 单脚本 50ms |
| 文件/网络/系统调用 | Rhai **默认无任何 IO/OS 能力**（纯计算） | 保持默认，不注册任何 IO 函数 |
| panic 宿主 | Rhai **Don't-Panic 保证**，错误走 `Result` | 落 trace `failure` |

**纪律**：
- 脚本**只读上下文变量，只返回值**，无副作用（不注册任何写外部状态的函数）。
- 引擎实例**每次求值新建或池化复用**，脚本间不共享可变状态（无跨请求污染）。
- 所有闸门参数**可配**（env / toml），默认保守，高级场景可放宽。

> 与 FEEL 的"受控、可静态校验、无副作用"（`cmx-rule-feel/src/lib.rs:11`）取向一致——脚本是"能力更强但仍沙箱"的一档。

## 7. 脚本上下文契约（能读什么、能调什么）

**脚本能读：**
- 决策图 Script 节点 / 脚本单元格：**当前累积上下文**的全部字段（输入事实 + 上游节点输出并入的字段）作为顶层变量。
- 脚本化子决策：**输入事实**的全部字段作为顶层变量。

**脚本能调：**
- Rhai **内置运算与标准函数**（算术、字符串、数组、map、类型转换等——Rhai 自带，远超 FEEL 内置库）。
- **脚本函数库**（P2）的已发布函数（`calcTax(...)`）。
- （不提供）任何 IO / 网络 / 时间 / 随机——保确定性与沙箱（如需当前时间，由输入事实传入，同 flow `now()` 注入纪律）。

**脚本须返回：**
- 一个 **map/对象**（Rhai `#{ key: value }`）→ 字段合并进上下文（Script 节点）或作为输出（脚本化子决策）。
- 或**单值**（脚本单元格 P1）→ 写入该输出格。

**值桥接**：`serde_json::Value ↔ rhai::Dynamic` 经 `rhai::serde` 双向转换。数值统一 f64（与 FEEL 引擎同偏差，一致）。

## 8. trace 与可解释性

脚本节点**完全纳入现有 trace 体系**（这是本引擎超越 ZEN 的招牌能力，脚本不能破坏它）：

每个脚本执行产一个 `TraceNode`：

```jsonc
{
  "nodeId": "calc", "nodeKind": "script",
  "matchedRules": [],              // 脚本无"命中行"概念，空
  "input": { …进入脚本时的上下文快照… },
  "output": { "tax": 12000.0 },    // 脚本返回值
  "timingUs": 340,
  "failure": null                  // 出错时："脚本节点 calc：第 3 行 变量 income 未定义"
}
```

**失败归因增强**：Rhai 的错误带**行号与位置**，比 FEEL 更精确。归因文案形如 `脚本节点 {id}：第 {line} 行 {rhai错误}`——审计中心（logs 页）与仿真台（simulator 页）**零改动**即可展示（它们已渲染任意 `nodeKind` 的 trace 节点）。

---

## 9. 完整性分析的影响

**诚实披露**：脚本是**黑盒**，gap/overlap 完整性分析**无法穿透**（无法对任意脚本做区域推理，这是理论限制，非实现偷懒）。

**处理策略**（与现有"含 not()/!= 无法结构化则显式告知"同纪律）：

| 载体 | 对 analyze 的影响 |
|------|------------------|
| Script 节点（图） | 图的 analyze 本就只聚合 `decisionTable` 节点，Script 节点**天然跳过**，无影响 |
| 脚本单元格（表） | 该**输出格**是脚本不影响判定（`inputEntries` 仍是 FEEL），gap/overlap 只看输入列约束，**照常分析** |
| 脚本化子决策 | 整体是脚本，analyze **显式返回**"脚本决策不参与完整性分析"（不静默） |

**关键设计**：让脚本只出现在**输出/计算**侧（Script 节点、输出格、子决策输出），**判定侧永远保持 FEEL**（决策表 `inputEntries`）——如此完整性分析对"决策表判定逻辑"始终有效，脚本只影响"算什么值"。这是**保住招牌分析能力**的架构约束。

## 13. 分阶段路线图

| 阶段 | 交付 | 验收 | 依赖 |
|------|------|------|------|
| **SC0 · Rhai 接缝** | `cmx-rule-feel/script.rs`（Rhai 求值 + serde 桥接 + 沙箱配置）+ `ExprEngine` 分派 | 单测：Rhai 脚本 `let x=1; x+1` → 2；沙箱超操作数报错；panic 不穿透 | 无（rhai 已缓存） |
| **SC1 · P0 Script 节点** | `GraphNode` 加 `lang`/`script`；`graph.rs` 加 `"script"` 分支；trace | 图含 Script 节点求值通；脚本出错落 `failure` 带行号；CDP 设计器建图 | SC0 |
| **SC2 · P1 脚本单元格** | `eval_output` 前缀 sniff `=rhai:`；designer fx 向导 | 输出格写脚本求值通；FEEL 格零回归；analyze 不受影响 | SC0 |
| **SC3 · P2 函数库** | `cmx_rule_script_function` 表 + `ScriptFunction` + CRUD 端点 + 求值前注册 + 管理页 | 定义 `calcTax` → 决策表/图/FEEL 都能调；发布/版本/删除；CDP 管理页 | SC0 |

| **SC5 · 加固** | 沙箱参数 env/toml 化；`/script/eval` 试算端点；脚本编辑器语法高亮；文档 | 沙箱压测（死循环被 kill）；使用手册补脚本章 | SC1–SC4 |

## 14. 风险与取舍

| 项 | 取舍 / 缓解 |
|----|------------|
| **脚本破坏可解释性招牌** | 架构约束：脚本只在**输出/计算侧**，判定侧永远 FEEL（§9）。gap/overlap 对决策表判定始终有效 |
| **脚本是黑盒难审计** | trace 记完整输入快照 + 输出 + 行号级失败归因（§8）；脚本体本身随版本发布**不可变留痕**（rev 哈希） |
| **业务人员写脚本门槛** | 定位为"**逃生舱**"非主路径——90% 用决策表/FEEL，脚本留给少数复杂场景；配语法高亮编辑器 + `/script/eval` 试算 + 函数库复用降门槛 |
| **DMN 互通性** | 脚本非 DMN 标准。导出 DMN 时 Script 节点降级为 `<functionDefinition>` 外部引用占位 + 注释保留源码；导入方需自行实现。**FEEL 部分仍完全 DMN 兼容** |
| **沙箱逃逸 / 资源耗尽** | Rhai 全套闸门（§6），默认保守，Don't-Panic 保证 |
| **f64 精度** | 与 FEEL 引擎同偏差（金额敏感场景注意），一致不新增问题 |
| **Rhai 单一维护者风险** | 与设计文档 §7 对 dsntk 的同款尽调纪律：Rhai 社区活跃度高于 dsntk，且 `ExprEngine` trait 抽象使其**可替换**（将来换 CEL/其它不锁死） |
| **性能** | 脚本比 FEEL 慢（解释执行 + 沙箱计数）。缓解：编译后 `AST` 缓存（同 key+version 复用编译产物）；高频路径仍推荐决策表 |

**坚决不做**：
- 不让脚本有 **IO/网络/系统**能力（保沙箱与确定性）。
- 不让脚本进入**判定侧**破坏完整性分析（保招牌能力）。
- 不用脚本**取代** FEEL/决策表（保 DMN 标准互通与声明式可读性）。

## 15. 附录：完整示例

### 示例 A · 决策图 Script 节点：阶梯个税（P0）

```jsonc
{
  "key": "payroll_tax", "name": "工资个税计算", "kind": "graph",
  "nodes": [
    { "id": "in", "type": "input" },
    { "id": "tax", "name": "阶梯个税", "type": "script", "lang": "rhai",
      "script": "let taxable = income - 5000;\nif taxable <= 0 { return #{ tax: 0.0, taxable: 0.0 }; }\nlet t = 0.0;\nlet brackets = [[80000.0, 0.45], [55000.0, 0.35], [35000.0, 0.30], [25000.0, 0.25], [12000.0, 0.20], [3000.0, 0.10], [0.0, 0.03]];\nlet b = taxable;\nfor br in brackets {\n  if b > br[0] { t += (b - br[0]) * br[1]; b = br[0]; }\n}\n#{ tax: t, taxable: taxable, afterTax: income - t }"
    },
    { "id": "out", "type": "output" }
  ],
  "edges": [ { "source": "in", "target": "tax" }, { "source": "tax", "target": "out" } ]
}
```

求值 `{income: 30000}` → `{tax: …, taxable: 25000, afterTax: …}`（脚本内循环累进，FEEL 表达不动）。

### 示例 B · 脚本函数库 + 决策表调用（P2）

**函数库：**
```jsonc
{ "name": "gradeScore", "params": ["raw"], "lang": "rhai",
  "body": "if raw >= 90 { \"优\" } else if raw >= 75 { \"良\" } else if raw >= 60 { \"中\" } else { \"差\" }" }
```

**决策表输出格调用（脚本单元格 P1）：**
```jsonc
"outputEntries": ["=rhai: gradeScore(score)"]
```

### 示例 C · 脚本化子决策（P3）

```jsonc
{
  "key": "dynamic_pricing", "name": "动态定价", "kind": "script", "lang": "rhai",
  "script": "let price = base_price;\nif demand > 0.8 { price *= 1.3; } else if demand < 0.3 { price *= 0.85; }\nif is_member { price *= 0.9; }\nprice = (price * 100.0).round() / 100.0;\n#{ finalPrice: price, surge: demand > 0.8 }"
}
```

被主决策图引用：`{ "id": "price", "type": "decision", "decisionKey": "dynamic_pricing" }`。
